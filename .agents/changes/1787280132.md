# The notch keeps two keys, and gives up a third

> Change `1787280132` — 2026-08-20

## Goal

Two edits to `[notch]`, pulling in opposite directions.

`corner-radius` was a setting with a range, a slider and a legend, and the cutout it is imitating has
exactly one radius. Every value on that slider except the built-in is a way to draw a strip that does
not line up with the hardware above it, so the range was nine parts wrong answer.

The other way: an app could name one notch colour, so a bare dot and a count of twelve drew the same
indicator. The glow has told those two apart per app since the cascade existed —
`[apps.Messages.glow.dot] enabled = false` is _glow for a real count, stay dark for a bare dot_ — and
the notch, which is the effect whose whole content is a colour, could not say it.

## Implementation

**The radius stops being config.** It comes out of `NotchSettings`, out of the reader, out of the
enumerable table and out of the shipped example, and lands as a private constant on the renderer that
draws it. The test that a value belongs in the file is whether a user could hold a preference about
it; a number whose only correct setting is the one macOS already drew fails that. Rejected: keeping
the key and marking it `advanced`, which moves a dial nobody should turn behind a disclosure triangle
rather than removing it — the dial is the problem, not its prominence.

**The notch cascades the way the glow does**, one level shallower:

```
ResolvedNotchItem.defaultColor  ⊕  apps.<App>.notch  ⊕  apps.<App>.notch.<count|dot>
```

There is no `[notch]` layer in the middle because `[notch]` describes the strip — placement, style,
how far it may grow — rather than an indicator, and a table that means two things at two depths is
the thing the glow's four uniform levels exist to avoid. So `NotchLayer` is the optional-everything
shape over the two keys an indicator has of its own, `AppNotch` becomes `base`/`count`/`dot` with
`layer(for:)` on top, and the built-in floor stays the Dock badge's red.

One consequence is worth stating because it is a behaviour change and not only a shape change:
`resolvedNotch` now reads `enabled` off the *overlaid* layer, so `[apps.X.notch] enabled = false`
with `[apps.X.notch.count] enabled = true` under it draws for counts and stays dark for dots. The
badge kind is the last word, which is what it already meant under `glow`.

**The name.** The cascade level wants to be called `NotchLayer`, because the reader of
`IMPLEMENTATION.md §4` should not have to learn a second word for `GlowLayer`'s idea. `PingUI` had
that name on its `CALayer` wrapper, so the wrapper is now `NotchStrip` — which is what every other
line already calls it (`window.strip`, "the strip" throughout the docs), and which says the thing on
screen rather than the framework type it is made of.

**One panel section, two effects.** `BadgeKindSection` is now generic over the layer it shows and the
rows that show it. Everything that made it worth having — the three-state override toggle, the hover
that previews the kind, and the `expand` that takes the braces off an inline table before a header
can reopen it — is identical for both cascades, and the alternative was a second struct differing
only in which rows it called. `NotchRows` gained an `inherited` colour for the same reason
`GlowLayerRows` has one: a colour first written at the kind level starts at the app's own colour, so
ticking the row on changes nothing by itself.

The shipped example needed the Messages block spelled long-form, because TOML will not let
`[apps.Messages.notch.dot]` reopen a `notch = {}` written between braces. That is the same constraint
`expand` exists for in the panel, so the example now demonstrates it rather than avoiding it.

**Verified by running the binary** on the 14" MacBook Pro against `BADGES`, with two stand-in apps:
`Alpha` green with a `dot` override of blue, `Bravo` orange with `dot` disabled. A count badge drew
Alpha green and nothing for Bravo's bare dot; flipping both badges drew Alpha blue and Bravo orange.
The strip's corners are unchanged with the setting gone. The settings window was driven to both tabs
through a temporary hook in `applicationDidFinishLaunching` — the Notch tab lists six settings and no
Corner radius, and the Apps tab shows Alpha's Notch section with a bare-dot override carrying blue
and a number override that is off.

## Observations

- **A file that already carries `corner-radius` now gets an unknown-key diagnostic by line**, and the
  line has to come out by hand. There is no migration path and the config machinery has no notion of
  a retired key; one setting is not enough to build one for.
- **There is still no `[notch]`-level colour.** A palette shared by every subscribed app is written
  once per app. Adding the layer is a fourth level and would make the two cascades the same depth,
  but nothing has asked for it, and the strip's own table is currently free of anything an indicator
  reads.
- The stand-in notch — a screen with no cutout of its own — is untouched by this and was not
  re-exercised; only the real cutout was on screen during verification.
