# The resource bundle is found by Ping, not by generated code

> Change `1787625093` — 2026-08-24

## Goal

The published `Ping.app` did not open. It trapped before any window, on its first resource read:

```
could not load resource bundle: from …/Ping.app/Ping_PingUI.bundle
                                  or /Users/runner/work/Ping/Ping/.build/…/Ping_PingUI.bundle
```

Neither path is anywhere a resource bundle is ever installed — the first is the app's root, which may
hold nothing but `Contents`, and the second is a build directory on a machine that stopped existing
when the job ended. The same commit built by hand produced a bundle that launched, so nothing in the
tree read as wrong, and only an archive off the runner reproduced it.

## Implementation

**`Bundle.module` is not one piece of code.** SwiftPM writes it per build, and which one it writes
depends on the toolchain. The newer accessor searches `Bundle.main.resourceURL`, then the framework's
resources, then `Bundle.main.bundleURL`; the older one checks `Bundle.main.bundleURL` and the
absolute `.build` path it was compiled against, and nothing else. Inside a bundle,
`Bundle.main.bundleURL` is the app's root and the executable's own directory is `Contents/MacOS`,
while the resource bundle is installed in `Contents/Resources` — so under the older accessor the app
looks in two places the bundle cannot be and dies. Which of the two a build gets is the build
machine's toolchain, and nothing in the package expresses a preference.

**The Makefile's `sed` over the generated file could not have worked.** It rewrote
`Bundle.main.bundleURL` to prefer `resourceURL` and then rebuilt — and SwiftPM rewrites derived
sources at the start of every build, so the rebuild the patch triggers is precisely what discards it.
The runner's log has the whole sequence: `Patched resource bundle accessor, rebuilding...`, then
`[0/4] Write sources`, then a recompile of `PingUI` from the regenerated original. It read as working
locally only because the branch never ran there: the newer accessor already contains the word
`resourceURL`, so the grep guarding the patch skipped it every time.

**So `PingResources.bundle` does the lookup itself**, over the three roots Ping runs from — the app's
`Contents/Resources`, the test bundle's resources, and the directory beside the binary in `.build`.
The generated accessor stops mattering because nothing calls it. Two alternatives were worse:
installing the resource bundle into `Contents/MacOS` satisfies the old accessor and breaks the new
one, since that path is last in its list and `Contents/Resources` is first; and copying the three
files directly into `Contents/Resources` to read them off `Bundle.main` gives up both `swift test` and
the unbundled binary, which is how the UI is looked at while it is being changed.

`fatalError` rather than `preconditionFailure` on the miss: under `-O` the latter traps with its
message dropped, and the run that started this was legible only because the generated code had used
`fatalError`. A packaging fault that exits 133 in silence is the expensive one.

**Verified against the configuration that failed, not reasoned about.** `swift build --build-system
native` is the runner's builder, and locally it reproduces both halves of the published archive: the
old accessor, and a flat `Ping_PingUI.bundle` with the resources at its top level instead of under
`Contents/Resources`. A bundle assembled from that build now launches and stays up; with the resource
bundle moved aside it dies naming all three roots it looked in. The default build system was then
re-checked end to end — bundle, unbundled binary, 92 tests, `make lint`.

## Observations

- **The two build systems emit different resource bundle layouts** — flat under `native`, a
  `Contents/Resources` bundle under `swiftbuild`. `Bundle` reads both the same way, so this needs
  nothing from Ping, but it means an archive's inner layout is not a signal that anything is wrong.
- **The suite cannot see this class of fault.** Under `swift test` the resource bundle is found
  through the test bundle's own resources, which was never the broken path — a green run says nothing
  about whether the assembled `.app` can find its font. The check that would have caught it is
  launching the built bundle, and the runner has no window server to launch an `NSApplication` on.
  Nothing here closes that gap.
- **The `v0.0.1` and `tip` archives already published are the broken build.** `tip` is replaced by the
  next push to `main`; a version is published once by design, so `v0.0.1` needs a new tag rather than
  a re-release.
- The bundle's name, `Ping_PingUI`, is now written in two places — the Makefile that copies it and the
  lookup that reads it. SwiftPM composes it from the package and target names and offers no way to ask
  for it, so the alternative to repeating it is deriving it, which is the same string with more steps.
