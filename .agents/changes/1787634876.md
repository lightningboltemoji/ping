# One switch per effect, icons in the app lists, and numbers that count

> Change `1787634876` — 2026-08-24

## Goal

Four complaints about the settings window, all of them about the surface rather than what it writes.

The Apps panel asked twice whether an effect applied: a switch at the top of the panel subscribed
the app, and then the effect's own section opened with an `Enabled` row that could turn off what had
just been turned on. Worse, `Enabled` was an `InheritableRow`, so the row read as a switch beside a
checkbox — two controls that both look like on/off, for one answer.

The app list was a plain `List` running the full height of the window. It holds itself off the tab
bar with a content inset, so the first app sat a hand's width down with nothing above it, and the
gap belonged to the list rather than to the window.

Neither list showed an app icon, in a panel whose whole subject is applications.

Adding an app from the Dock subscribed it to the glow on the spot, which is an effect nobody asked
for on somebody's screen, and left a `[apps.X] glow = {}` behind for an app the user may only have
been looking at. The app's own notch row offered to inherit its colour, from nothing: `[notch]`
describes the strip and has no colour to inherit.

And every number was a continuous slider, so a maximum width could be set to 182.55 px — precision
no screen has and the reading printed anyway.

## Implementation

**The app-level `Enabled` row is gone, and the subscription switch took its meaning.** The two say
the same thing at that level: `resolvedGlow` returns `nil` for an app with no `glow` table and for
one whose `enabled` resolved false, and the panel cannot show a difference between them because
there is none on screen. So the switch reads `table != nil && base.enabled != false`, and turning it
back on removes an `enabled = false` the file already carried rather than writing `true` beside it.
Turning it off still takes the whole table out — unsubscribing is what the control has always meant,
and it is what the `−` button means too.

The alternative was to keep the row and only restyle it, which was considered and dropped: the
second control's only reachable state was one the first already had. `IMPLEMENTATION.md §4` still
describes three ways to resolve to `nil` because the *file* still spells all three; what changed is
that the window offers one control for two of them.

**A badge kind keeps a switch, because it is load-bearing.** `[apps.Messages.glow.dot] enabled =
false` — glow for a real count, stay dark for a bare dot — is in the shipped example config and no
other control in the panel can say it. It is a plain two-state toggle rather than an inheritable
row: it reads the cascade (`kind.enabled ?? base.enabled ?? true`) and writes only a disagreement,
so a kind that agrees with its app says nothing at all. That keeps "writing the default takes the
line out" true one level deeper, and it means the double checkbox is gone at both levels — the
inheritable rows are now exactly the *value* rows, which is what they were for.

`BadgeKindSection` takes the two booleans as plain values rather than reading them off the layer,
because the call site already has the concrete `AppGlow`/`AppNotch` in hand. A protocol over the two
layer types would have put a UI concern in `PingConfig` to save four arguments.

**The sidebar keeps the list style it had**, and the clearance above its first row with it. That the
gap cannot go was measured rather than assumed: `AppKitWindowHostingView` reports an 88pt top safe
area for the tab bar, which is drawn across both panes, and three ways of refusing it were tried and
reverted — `.safeAreaPadding(.top)` and `.ignoresSafeArea` + `.padding` are no-ops or double-count
here, and `.ignoresSafeArea` with a smaller content margin does raise the rows, straight under the
titlebar material, where they render visibly washed out. The gap is the price of a tab bar over a
split view.

`.listStyle(.sidebar)` was tried for it and backed out. It gives the standard source-list metrics and
drops the separators, but a source list is a vibrant one: the column turns translucent and picks up
the wallpaper and whatever effect Ping is previewing behind the window. An opaque list that starts
low beats a transparent one that starts in the same place.

**Picking an app from the Dock writes nothing.** Which effects it gets is the question the panel is
there to ask, and answering it with a glow is `PRINCIPLES.md`'s "an effect nobody asked for is on
somebody's screen". The name is carried in the panel's own state and shown as a row with all three
switches off; throwing one writes the app's first line. Nothing to prune at save, because nothing was
written — the alternative, writing `[apps.X]` on add and dropping empty app tables when saving, would
have made the window rewrite blocks it did not author, and it would have deleted a hand-written empty
`[apps.Slack]` along with the ones it made.

**Blank is a state a row is allowed to be in**, and that is the whole of it: the list holds as many
as it needs, they survive moving between apps and adding another, and unticking an app's last effect
leaves its row too — swapping one effect for another should not take the row out from under the
pointer. `−` is the only thing that removes one, and it moves the selection off the row before
unsetting so that the removal is not read as a last effect coming off and the blank row put straight
back.

The first cut modelled it as a transient instead: one name, cleared as soon as the selection moved.
That replaced the app you had just added the moment you clicked another, which is the shape of the
mistake — a row is a row, and one the file has no line for is still a row.

**The app's own notch colour is a well, not an inheritable row.** The cascade above it is
`ResolvedNotchItem.defaultColor` and nothing else, so "inherited" was offering to defer to a setting
that does not exist. Without a checkbox to take the line out, choosing the red the indicator already
draws is what does — the rule the rest of the window keeps, one level deeper. Under a badge kind the
row stays inheritable, because there the app's own colour is a real thing to defer to.

**Icons come from the Dock reading**, which already carries a URL per app so that `BadgeSnapshot`
can stay a value type. `IconCache` becomes process-wide (`IconCache.shared`): a third surface wants
the same icons keyed the same way, and three private caches would read the same files three times.
It grows one method, `image(_:from:)`, that loads and returns in a step, because a SwiftUI view has
nowhere to put a separate loading pass. An app the file lists that is not in the Dock has no URL and
draws `app.dashed`.

**A number's granularity moved onto its unit.** `Setting.Bound` carries a `step` instead of an
`isIntegral` flag, and `isIntegral` is derived from it; `Setting.Unit` says what the step is — whole
points, tens of milliseconds, twentieths of a ratio. Every default in the table lands on a detent, so
no existing file is a value the slider cannot reach, and the reader is untouched: a hand-written
`icon-size = 32.5` still parses, it is only what a control produces that is snapped.

The sliders stay continuous and snap in the binding rather than taking `step:`. AppKit draws one tick
per detent for a stepped slider, which is a scale at a dozen of them and hatching at six hundred —
`max-width` spans 600 points. Snapping on the way out gets whole-pixel values with a clean track, and
because the binding reads back the snapped value the thumb still rests on detents.

**Verified by running the binary** against a scratch config, with a temporary hook in
`applicationDidFinishLaunching` that opened the window on a given tab and selected a given app — the
Dock's own reading was stubbed there too, since a rebuilt ad-hoc binary loses its Accessibility
grant. The Apps panel showed one checkbox per effect and no `Enabled` row; Messages, whose config
carries `glow.dot.enabled = false`, showed `Override` on with a single unchecked `Glow` beneath it
and every value row still inheriting. Music, whose config is `notch = {}`, showed one Color well on
red with no checkbox beside it. `+` then an app from the popover left Discard greyed — the draft
still clean, nothing written — and ticking `Glow` on that row turned the footer to Unsaved without
the row moving. Two apps added in a row both stayed, and both were still there after selecting a
third; unticking Music's only effect left its row selected and blank; `−` took it away and moved the
selection on. The Notch tab read `120 px`, `185 px`, `8 px`, `350 ms`.

## Observations

- The gap above the first app is unfixed. Moving the list up means moving rows under a translucent
  tab bar, and the one style that would have made the gap look deliberate — a source list — buys it
  by making the whole column transparent.
- The hover glow reported in that gap was never reproduced under a synthetic pointer warp — SwiftUI's
  `onHover` did not fire for a warped pointer even over a real row, so the test was inconclusive
  either way. The list still extends under the bar; if the glow persists, that inset region is where
  it comes from.
- A file that says `apps.X.glow.enabled = false` *and* `apps.X.glow.count.enabled = true` reads as
  off at the top and on for counts, which is literally what it says but looks self-contradicting. No
  control the window offers can produce it.
- The Add-from-the-Dock popover closes on a pick by writing the `isPresented` binding rather than by
  `dismiss()`, which shuts the popover without putting the flag back — leaving a `+` that does
  nothing until something else toggles it.
- Ratio sliders step by 0.05. That is fine for opacity and size, whose whole ranges are a unit wide,
  but it is the one step chosen for feel rather than because the quantity is counted that way.
