# The strip's coordinate space

> Change `1787213632` — 2026-08-20

## Goal

With `placement = "left"` or `"right"`, most of the indicators were not on screen. Four dots in the
left extension drew as two, jammed against the outer edge, with the first two of the list missing
entirely; `split` was correct. Nothing was near `max-width`, so this was not the tail overflowing —
it was the indicators being drawn in the wrong place and `masksToBounds` eating what fell outside.

## Implementation

The strip's shape was given bounds centred on *itself* — `x = −width/2 … +width/2` — while
`NotchLayer.x(of:on:of:)` measures a slot from the **notch**. The two agree only when the extensions
are equal, which is exactly `split`. Everywhere else the shape's middle sits half the difference
between the sides away from the cutout, and every indicator rode that offset out of the shape: with
one side open by `L` the whole set moved `L/2`, and an extension sized to fit its slots has only `L`
to give.

The fix is to anchor the bounds on the cutout instead — `x` runs from −(left + half the cutout) to
+(right + half the cutout) — so `x = 0` is the notch's middle whichever side is opening, which is
what the slot arithmetic already assumed. Rejected: adding the offset inside `x(of:on:of:)`, which
would make the slot arithmetic carry the shape's asymmetry and needs the two widths threaded down to
a function that knows only about slots. One coordinate space, decided once, is the smaller object.

The property that made a centred bounds attractive survives, and it is worth stating why: a sublayer
must not appear to move while the strip opens. `bounds` and `position` animate under one
`CATransaction`, so at every frame the origin's slide left and the position's shift right cancel —
the indicator renders at the same screen point from the first frame to the last, and the opening
strip *reveals* it rather than carrying it.

`NotchLayerTests` is new and is the first test over `NotchLayer` itself: it hangs the strip in a host
layer the size of the window `NotchWindow` would build, so a sublayer's frame can be read in the
window's own coordinates, and it asserts in all three placements that the innermost indicator is one
`gap` from the cutout and that none of them lies outside the shape that masks them. Both tests fail
on the old bounds for `left` and `right` and pass for `split`, which is the reported symptom exactly.
One wrinkle: `#expect(a == b)` compares `false` for equal values when one side is `CGFloat` and the
other `Double` — the implicit conversion does not survive the macro — so the test converts to `Double`
before comparing.

**Verified by running the binary** against `BADGES` on the 14" MacBook Pro (cutout 220×38 at x=790),
four dots at `item-size` 8 and `gap` 8. All three placements now draw all four in file order, packed
against the cutout. At `grow-ms` 5000 the strip was caught mid-open with the innermost dot already at
its final x and the rest still behind the closing edge, arriving as the edge swept past them — the
reveal, with nothing sliding.

## Observations

- The window is built at the strip's widest, so the old offset only ever clipped against the shape,
  never against the window. Nothing was drawn outside the strip at any point.
- `split` is untouched by this and always was: it is the one placement whose two widths are equal by
  construction, which is why the defect shipped.
- The stand-in notch still has no hardware here to check. Its resting bounds are zero-width and the
  cancellation was re-derived for a shape growing from nothing, but that path is arithmetic only.
